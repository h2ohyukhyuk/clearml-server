# Local ClearML Server

Docker Compose deployment for a local ClearML management server, adapted from the [official ClearML Server v2.4.0 Compose file](https://github.com/clearml/clearml-server/blob/v2.4.0/docker/docker-compose.yml).

This project runs the API server, web UI, file server, MongoDB, Redis, Elasticsearch, and the asynchronous file-deletion service. Training agents run separately. Service images use fixed version tags, and persistent data is stored in directories relative to `compose.yaml`.

## Requirements

- Linux with Docker Engine and the Docker Compose plugin.
- Enough memory for all services. The current Elasticsearch settings were chosen for a 64 GB machine shared with training workloads: a 4 GB JVM heap and an 8 GB container memory limit. These are deployment settings, not a minimum-memory specification.
- Available local ports `8008`, `8080`, and `8081`.

## Initial setup

From the cloned project directory, create the directories used by bind mounts:

```bash
mkdir -p config logs data/fileserver data/elastic_7 \
  data/mongo_4/db data/mongo_4/configdb data/redis
```

Configure the kernel setting needed by Elasticsearch and set ownership of its data directory:

```bash
echo 'vm.max_map_count=524288' | sudo tee /etc/sysctl.d/99-clearml.conf
sudo sysctl -w vm.max_map_count=524288
sudo chown -R 1000:1000 data/elastic_7
```

This Compose file uses literal configuration values and does not require a `.env` file. The `config/` directory can hold local ClearML Server configuration overrides and is excluded from Git.

## Start and stop

```bash
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail 100 -f
```

The first startup may take several minutes to download images and initialize databases. A running container does not by itself confirm that its service is ready. Omit `sudo` if your user has Docker access.

| Service | Local address |
| --- | --- |
| Web UI | http://localhost:8080 |
| API | http://localhost:8008 |
| File server | http://localhost:8081 |

Create API credentials in the web UI under **Settings > Workspace** and configure them in your training clients and agents. Do not commit credentials to this repository.

Stop the server with:

```bash
sudo docker compose down --timeout 120
```

Persistent data remains in the local `data/` directory.

## Connect the ClearML Agent

Use this server together with [clearml-agent](https://github.com/h2ohyukhyuk/clearml-agent). The server stores task information, metrics, and uploaded artifacts and provides the web UI and queues. The agent watches a queue and launches training containers on its training host. Start the server first, then configure and start the agent in its own project directory.

### Server and agent on the same Linux host

1. Start this server using the commands above and open http://localhost:8080. Create API credentials under **Settings > Workspace**.
2. Clone the agent repository if you do not already have it, then create its local configuration:

   ```bash
   git clone https://github.com/h2ohyukhyuk/clearml-agent.git
   cd clearml-agent
   cp .env_bak .env
   chmod 600 .env
   ```

   If the agent repository already exists, enter that directory and create `.env` only if it does not exist. Keep an existing `.env` and edit it instead of overwriting it.

3. Set the following values in the **agent project's** `.env`, entering the credentials generated by this server:

   ```dotenv
   CLEARML_API_HOST=http://localhost:8008
   CLEARML_WEB_HOST=http://localhost:8080
   CLEARML_FILES_HOST=http://localhost:8081
   CLEARML_API_ACCESS_KEY=
   CLEARML_API_SECRET_KEY=
   AGENT_WORKER_ID=training-worker-1
   AGENT_QUEUE=default
   ```

   The empty key fields above are placeholders; fill them before starting the agent. These `localhost` URLs work because the agent and its training containers use Linux host networking. The server itself does not need an `.env` file for this connection.

4. In the same agent `.env`, set `AGENT_HOST_DIR` to the absolute agent project path and configure the dataset paths, `WORKER_GPUS`, and `TRAINING_IMAGE`. Create `AGENT_HOST_DIR/cache` and make sure the dataset directory exists. Prepare the training image on the training host before submitting tasks. See the [agent README](https://github.com/h2ohyukhyuk/clearml-agent#readme) for image build commands and all environment variables.
5. Start the agent from the **agent project directory**:

   ```bash
   sudo docker compose up -d --build
   sudo docker compose logs --tail 100 -f agent
   ```

   This builds the agent image from `dockers/agent/` and starts the worker service. The PyTorch image in `dockers/torch:2.9.1-py3.12-cu128/` is a separate training image and must be built separately or otherwise made available on that host.

6. Open **Workers & Queues** in this server's web UI and confirm that `training-worker-1` is online and listening to `default`. Submit training tasks to that queue. An online worker waits until tasks are submitted; starting the server and agent does not start training by itself. Training code must configure its own ClearML connection and task submission.

Run server commands from the server project directory and agent commands from the agent project directory. They are independent Compose deployments. Keep the agent's `.env` and its API credentials out of Git.

### Agent on another server

The current server Compose binds its published ports to `127.0.0.1`, so a remote agent cannot connect with this configuration unchanged. First configure remote access as described below. Then set all three `CLEARML_*_HOST` URLs in the agent's `.env` to the management server's reachable IP or DNS name with the appropriate ports or reverse-proxy endpoints. Use API credentials issued by this same ClearML Server.

The remote training host needs its own Docker setup, GPU support, training image, and dataset mounts. ClearML Server does not build or distribute training images or copy your local dataset directory to remote workers.

## Local access and remote workers

Published ports bind to `127.0.0.1`, so this configuration accepts clients on the same machine only. It does not enable access from other training servers.

For remote access, configure a stable server address, authentication, firewall rules, and TLS as needed. Update port bindings and the file-server URL settings in Compose consistently. Clients and agents must use addresses reachable from their machines; `localhost` on a remote training host points to that host, not this management server. Do not expose the default deployment to an untrusted network without access controls.

## Persistent files and migration

| Path | Contents | Included in Git |
| --- | --- | --- |
| `compose.yaml` | Service definitions and image versions | Yes |
| `data/` | Databases, experiment events, and uploaded files | No |
| `config/` | Local server configuration overrides | No |
| `logs/` | Server logs | No |
| `.env` and local environment variants | Optional local settings and credentials | No |
| `compose.yaml.before-*` | Local historical Compose backups | No |

A Git clone contains deployment files, not existing experiments or server state. For migration, stop training clients and the server first, then copy the deployment directory including ignored files, hidden files, permissions, and ownership. Start with the same image versions and CPU architecture on the destination. Configure Docker and the kernel setting there as well. Docker images are not stored in this directory and must be downloaded or transferred separately. Models and datasets stored outside this directory need their own backup.

## Elasticsearch memory

The following settings are already included in `compose.yaml` and take effect when you start the server with `docker compose up -d`:

```yaml
ES_JAVA_OPTS: "-Xms4g -Xmx4g"
mem_limit: 8g
```

Elasticsearch uses a fixed 4 GB JVM heap and an 8 GB container memory limit. The container limit also covers memory outside the JVM heap. No additional memory configuration or separate Elasticsearch recreation command is needed for the supplied settings. These values were chosen for a 64 GB machine shared with training workloads; adjust them if your machine or workload requires different limits.
